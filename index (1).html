    Range Companion: answering “will I make it?” instead of “how many km?”

    Riders already see battery percentage and a range number. What they actually want to know is whether they’ll reach where they’re going, and if not, the one thing to do about it. Range Companion combines the route ahead, the ride mode, the weather and how this rider actually rides to answer that in one glance.

    Answer the question, not the metric

    “80 km range” makes the rider do arithmetic. “You’ll arrive with about 34%” doesn’t. The headline is always the outcome of this trip.

    A glance, not a read

    Headlines stay under eight words, status is carried by wording as well as colour, and the screen never changes state faster than once a minute.

    One action, one tap

    When a trip is at risk the screen offers exactly one fix, the cheapest one that works: Eco mode first, a charging stop only if Eco isn’t enough.

    Learn the rider, then trust them

    The estimate starts from a route-aware model and shifts toward this rider’s real consumption as kilometres build up. The likely range narrows as it learns.

    Warn on the cautious number

    Decisions use the pessimistic end of the likely range, not the average. Showing a confident average and being wrong costs more trust than an early, honest heads-up.

    Calm when nothing’s wrong

    Most rides are routine. The comfortable state is quiet and neutral, and a suggestion the rider dismisses stays dismissed unless things get worse.

    Implementation spec

    Written so a vehicle software team could build it. Values marked as thresholds are starting points for calibration in shadow mode, not final numbers.

    How the estimate works

    1. Split the remaining route into segments. For each, predict energy from the expected speed (speed limit, traffic, mode ceiling), gradient (uphill costs, downhill regenerates) and weather.
    2. Track a rolling ratio of actual to expected energy, weighted by distance, so recent riding counts most. This captures riding style, load and tyre pressure without measuring any of them.
    3. Blend the model with the learned ratio. Trust in the rider’s data rises from 0% toward 100% over the first few kilometres.
    4. Put an uncertainty band around the result. It starts wide, narrows as trust grows, and widens again in rain.
    5. Convert to arrival charge as a cautious (P10), likely (P50) and optimistic (P90) value. States are decided on P10 and P50; the rider sees P50.

    Timing rules prevent the screen from flickering: a more serious state must hold for 60 seconds before it shows, a less serious one for 3 minutes. “Not now” snoozes the suggestion for 10 minutes, unless the trip moves to Won’t reach. Accepting an action re-evaluates immediately so the rider sees its effect.

    Edge cases

    SituationBehaviour
    No destination setNo trip verdict. Show range only, with a one-time “Set a destination to check this trip” prompt.
    GPS or navigation lostHold the last estimate, keep learning from distance, and add “Estimate paused” if the outage passes 2 minutes.
    First 2 km of a rideRider data has little weight, so the band is wide and warnings rely on the model.
    Rider changes modeRe-estimate with the new mode at once; the learned riding ratio carries over.
    Charger offline or fullSkip it in suggestions; if it was the planned stop, offer the next one with a new headline.
    Long downhillRegeneration improves the estimate, but de-escalation still waits 3 minutes.
    No charger reachableRecommend Eco and the lowest-consumption speed instead of a stop; never show an action that can’t work.

    How we’d know it works

    • Calibration: actual arrival charge falls inside the likely range on at least 80% of trips, with median error under 3 points.
    • No surprises: trips ending below 5% that weren’t flagged at least 10 minutes earlier should be close to zero.
    • Useful, not noisy: high acceptance of suggestions, low “Not now” rate, and no drop in the share of rides that stay Comfortable after launch.

    Rollout

    1. Shadow mode: compute and log on vehicles with nothing on screen, then calibrate thresholds and band width against real trips.
    2. Internal riders: turn on the screen and review dismissals and false alarms weekly.
    3. Opt-in beta through a settings toggle, then default on.

    GoalFlow
    
        
    Goal setting and performance tracking portal. Built in 48 hours for the Atomberg Technologies hackathon, then redesigned.
    
        
    The problem
    
        
    Employees, managers and admins open the same portal with different questions. An employee asks “am I on track?”, a manager asks “who needs help?”, an admin asks “is the cycle set up right?”. One dashboard for all three answers none of them.
    
        
    What I did
    
        
    Role-based views over three permission levels, so each role lands on its own question first, with live updates over WebSockets so managers see check-ins without refreshing.
    
        
    The Q4 projection was a table of percentages, which made people do the comparison themselves. The redesign leads with the answer (“2 of 3 goals on course for 80% by Q4”), names the goal furthest behind and by how much, and gives every goal a small line: solid for real check-ins, dashed for the projection, against the 80% target.
    
        
    Built with
    
        
    React 18, Vite, Node.js, Express, JWT auth, WebSockets, 30+ REST endpoints. Deployed on Vercel and Render.

    TrackPulse
    
        
    Project management portal with AI delay-risk analysis. Solo project.
    
        
    The problem
    
        
    A red “critical” badge with no explanation gets ignored or argued with. And an AI feature can fail: if the model is unavailable, the page shouldn’t go blank or pretend nothing changed.
    
        
    What I did
    
        
    The first risk page showed counts per level and didn’t render properly, because its styles depended on a library that was never installed. I rebuilt it around one sentence (“6 of 6 projects are likely to miss their deadline”) and a card per project listing exactly which rules fired: schedule used versus work done, days overdue, critical delay factors, staffing gaps.
    
        
    Each card ends with one suggested next step from the analysis engine, which calls the Claude API and falls back to rules when it can’t. The card always says which one produced it, so trust in the AI version stays honest.
    
        
    Built with
    
        
    React, Node.js, Express, SQLite, Claude API with a rule-based fallback.
    
        
    Code on GitHub
    
      
    
    
    

    
    
      
      
    
        
    RightSize AI
    
        
    Predictive autoscaling for Kubernetes. Cloud Product and Platform Engineering course project.
    
        
    The problem
    
        
    Default autoscaling reacts after traffic arrives, so users feel the spike before capacity catches up. Predicting ahead fixes that, but operators won’t hand control to a forecast they can’t see.
    
        
    What I did
    
        
    A FastAPI service forecasts load with Prophet and decides whether to scale. The original dashboard showed one predicted number. I added an endpoint that returns Prophet’s full forecast with its uncertainty interval, and redesigned the screen to lead with the decision in a sentence, draw the likely range against the scale-up and scale-down thresholds, and explain that the plan uses the top of the range so capacity is ready if the peak lands high.
    
        
    When Prometheus isn’t connected the service runs on generated load, and the dashboard says so instead of presenting it as live.
    
        
    Built with
    
        
    FastAPI, Prophet, React, Recharts, Tailwind. Scaling is applied with kubectl; a dedicated Kubernetes operator is the next step.
    
        
    Code on GitHub
    
      
    
    
    
  
    

    


    
  
    
    
    How I work with AI in design
    
    
    
      
    
        
    Start from the decision
    
        
    Before any screen, I write down what the person needs to decide and what would change their mind. The model’s output is shaped around that decision, not the other way round.
    
      
    
      
    
        
    Prototype in real code early
    
        
    Predictions behave differently with real inputs. A working prototype, like the dashboard above, shows edge cases a static mockup hides: the 4% battery, the 90 km trip, the rainy day.
    
      
    
      
    
        
    AI for breadth, judgment for the cut
    
        
    I use AI tools to generate many directions quickly, then throw most of them away. GoalFlow’s interface went through several rebuilds because the fast versions all looked the same.
    
      
    
      
    
        
    Design the failure state first
    
        
    Every AI feature I build has a defined fallback and a way to say “less sure”. If a product only works when the model is right and available, it isn’t finished.
